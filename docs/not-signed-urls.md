# Removal of pre-signed URLs

Pre-signed URLs have been removed from this plugin as of version 1.2.0, released in April 2025.

**ACTION REQUIRED**. If you were using an S3 (or S3-compatible) bucket without a CloudFront CDN distribution, you will need to make sure all your files are stored with Public Read ACLs on your bucket. This plugin will no longer work with files that have Private ACLs. You can use a third party tool or application such as CloudBerry, CyberDuck, or `s3cmd` to change the ACLs of your files. While you can use Amazon S3's file manager, we do not recommend this as it requires you to change the ACLs of each file, one by one, which is extremely tedious.

## What happened

When the plugin was first created in 2022 it was always creating pre-signed URLs with a validity time of 10 years. This was great, as it allowed you to insert images and media files links into your content, which would be valid for ten years. This is much longer than the typical site is updated, and the content rewritten or, at least, retouched.

Over the following years, Amazon S3 reduced the maximum validity time of pre-signed URLs to **7 days**, with a default of **one hour**. This meant that pre-signed URLs were practically useless. Inserting any image or media file into your content as a pre-signed URL would require you to come back within an hour and redo it.

This meant that for the last nearly two years the only way to correctly use this plugin was to set up a CloudFront distribution of your S3 bucket. Anything else would simply result in errors.

## Alternatives we considered

This problem stems from the way the Joomla Filesystem API works. It only asks for the URL to the media file _at the time the media file is selected in the interface_. From that point onwards it is “frozen in time”. While this works great for static URLs, it does not work at all when the URL to the media file expires at some point, as is the case with pre-signed URLs.

We did consider several alternatives. The common idea behind them is how you can create a static URL which will result in a “fresh” pre-signed URL being used when the content is loaded. And that's where problems begin to crop up.

One solution is using a ‘fake’ URL that uses com_ajax to go through the plugin to fetch a new URL for the media file. The downside to that is that it takes two requests for each file: one made by your browser to your site to load this proxy URL, and one request from your site to S3 to download the file and ‘proxy’ it to the browser. This vastly increases the load on your server. To reduce the load, we'd have to cache all media files served that way, which completely negates the entire point of using storage external to your site! Moreover, not all servers would allow this method to work reliably. As a result, this was never implemented.

The other option was to also ship a `system` plugin which looks for media files generated by this plugin and create a newly signed URL for them, replacing what you already had on the page. This is problematic on many counts. You now need yet another plugin to run on your site. There are complications when caching is used. The pre-signed URLs don't have a human- or machine-readable expiration date, which would require creating new signed URLs for _all_ media files handled by this plugin on every page load. Even so, being able to find these URLs and reverse-engineer the bucket and path to them was very slow and error-prone. As a result, this was never implemented.

There are other variations of the same ideas such as using plugin codes (something like `{s3media bucket /path/to/file}`) but they all resolve to the same problems of one of the previous two ideas: you either need to proxy the files through your site (slow, will consume too many server resources), or you end up rewriting URLs which is slow and error-prone. 

Please do not ask for this feature to come back; it won't. 

You're, of course, welcome to submit a Pull Request with your idea to solve this problem. If you do, please don't be upset if you are told how your solution is equivalent to one of the already considered alternatives, making it a non-starter. Do keep in mind we only mentioned the two most obvious alternatives we considered. There are another six or so alternatives that crossed our mind. We didn't mention them above because –as we said– they ultimately result in the same two sets of problems.

## Why we made the change

This meant that for the last nearly two years the only way to correctly use this plugin was to set up a CloudFront distribution of your S3 bucket. Anything else would simply result in errors.

As a result, we removed the use of pre-signed URLs to allow use of this plugin with any S3 bucket, even when not using a CDN. This means that only files with Public ACLs can be used with this plugin.

If you had uploaded files with this plugin in the past you will need to change their ACLs to Public. We recommend using a third-party tool or application such as CloudBerry, CyberDuck, or `s3cmd` to change the ACLs of your files _en masse_. While you can use Amazon S3's file manager, we do not recommend this as it requires you to change the ACLs of each file, one by one, which is extremely tedious.
